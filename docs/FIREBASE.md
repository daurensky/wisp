# Firebase и соединения через интернет

В сборку включена публичная клиентская конфигурация проекта `wisp-dd1ec`. Веб-SDK не нужен: нативное приложение использует Firebase Authentication REST и Realtime Database REST по HTTPS. Пароли в SQLite не копируются; Firebase refresh token хранится через Windows DPAPI для текущего пользователя ОС. SQLite остаётся кэшем истории и медиа. Старые локальные аккаунты не превращаются автоматически в Firebase-аккаунты: один раз зарегистрируйтесь с email в обновлённом приложении.

## Настройка владельцем проекта

1. В Firebase Console → Authentication → Sign-in method включите Email/Password. В этой ветке тесты выполняются на fake HTTP и demo-эмуляторе; агент не меняет производственные аккаунты или данные.
2. Откройте Realtime Database → Rules. Вставьте **весь** файл [database.rules.json](../firebase/database.rules.json) и нажмите Publish. Не включайте публичное чтение/запись базы. Клиентская конфигурация не даёт административных прав, поэтому приложение не может опубликовать правила за владельца.
3. Запустите новую сборку. Зарегистрируйтесь с email и именем. Следующие запуски восстанавливают Firebase-сессию. «Выйти из аккаунта» находится в меню значка трея.
4. Создайте сообщество и отправьте другу приглашение `wisp-cloud:…` через кнопку «Пригласить». Он регистрируется в том же проекте и вставляет приглашение кнопкой ↗. Код сообщества служит приглашением: доступ получает тот, кому известен непредсказуемый идентификатор; отдельных ролей и отзыва приглашений пока нет.

Профили, состав сообществ, каналы, последние 100 сообщений выбранного канала и присутствие синхронизируются через Firebase. Обновление присутствия — примерно каждые 5 секунд; при аварийном выходе отметка исчезает у клиентов через 45 секунд. Кнопка выхода из голосового канала не закрывает сообщество. Любой участник может первым войти в голосовой канал; остальные подключаются к нему напрямую через сигналинг Firebase.

## Прямой голос WebRTC со STUN

В режиме Firebase голос и демонстрация используют полноценную сетку WebRTC между участниками, до четырёх прямых соединений на пользователя. Владелец сообщества не является ретранслятором и может уйти из разговора. Настройка портов и VPN для установки соединения не требуется, если сеть допускает ICE hole punching.

По умолчанию используются `stun:stun.l.google.com:19302` и `stun:stun1.l.google.com:19302`. Настройки профиля → «Сеть · STUN» позволяют задать до восьми UDP STUN URL, по одному на строку. Они сохраняются в `%LOCALAPPDATA%\Wisp\network.json`; пустой список означает только локальные ICE-кандидаты. TURN исключён из этой доработки по решению владельца; статичных учётных данных и сервера выдачи секретов нет. При симметричном/строгом NAT, блокировке UDP или недоступном STUN прямое соединение может не установиться. После неудачи пара автоматически повторяет согласование с новым Attempt через 2/5/15/30 секунд, затем показывает окончательную ошибку. Disconnected через 5 секунд запускает ICE restart; смена адреса сети обрабатывается с debounce. Для уже номинированной пары restart в 10.0.17 сохраняет completed checklist; клиент распознаёт это и сразу переходит к новой паре через backoff. Эти повторы не устраняют ограничения NAT. Работу между любыми двумя интернет-сетями без TURN гарантировать нельзя.

Сигналинг SDP/ICE проходит через Firebase. Места в канале хранятся в `rtcRooms`: сервер допускает только пять фиксированных слотов s0–s4 и проверяет владельца слота при атомарной записи. Клиент обновляет место каждые 10 секунд, неактивная запись освобождается после 45 секунд. Сигналы доступны только соответствующей паре участников канала и связаны со свежими идентификаторами сессий. При потере продления места клиент останавливает транспорт, чтобы не обходить лимит.

Hardening требует **весь файл правил** с rtcRooms, rtcSignals и rtcCandidates, обязательными Attempt/CreatedAt. Порядок публикации относительно запуска клиента приведён ниже; смешанный выпуск несовместим.

Голос передаётся как стандартный Opus в отдельной дорожке SRTP (48 кГц, моно, 20 мс, 32 кбит/с). Ещё одна дорожка SRTP передаёт стереозвук демонстрации (Opus, 96 кбит/с); третья — H.264-видео с RTP-фрагментацией. SCTP остаётся для файлов и небольших команд, поэтому загрузка файла или кадра не занимает очередь микрофона. По решению владельца TURN не добавляется; лимит пяти мест сохраняется.

Экран кодируется Windows Media Foundation: до 1080p/60, по умолчанию 1080p/30, 4 Мбит/с на каждого зрителя. CPU и сеть ограничивают фактическую частоту; очереди ограничены, декодер после потери/перегрузки ждёт следующий IDR. Параметры кодека повторяются для позднего входа; зритель запрашивает IDR при потере синхронизации не чаще раза в секунду, плановый GOP — 3 секунды. WGC захватывает окна/мониторы с курсором; GDI остаётся резервом и для объединённого рабочего стола. Сворачивание ставит показ на паузу, закрытие останавливает. Защищённые окна и часть GPU-окон в резервном GDI могут давать чёрный кадр. RTCP-потери снижают общий битрейт/FPS. FFmpeg не нужен; аппаратное кодирование не гарантируется.

Звук демонстрации использует Windows process-loopback (build 20348+): выбранный процесс с дочерними процессами, а для монитора — весь системный звук с исключением Wisp. На Windows 10 этот вид захвата недоступен, видео продолжает работать. Микрофон использует WASAPI Communications; AEC/NS/AGC зависят от драйвера. Есть FEC/PLC, адаптивный буфер и выбор/смена устройств голоса, но аппаратное эхо/качество ещё требуют ручной проверки.

Новые вложения и голосовые сообщения хранятся в `communities/{community}/files/{hash}`: `Chunks/c00`–`c31` по 512 КиБ и `Info` после полной загрузки. Чтение и создание доступны только участникам. Части и опубликованные метаданные неизменяемы; условный REST PUT `if-match: null_etag` позволяет безопасно повторить незавершённую отправку. Проверяются SHA-256, размеры частей, общий размер и полнота файла. `Info` содержит только `Name`, `Kind`, `Size`, `Chunks`.

Старые `profiles/{uid}/Files` не удаляются и не мигрируются автоматически: новые правила разрешают чтение только автору и запрещают новые записи. Получатели сохраняют уже скачанные локальные копии. Автор может заново отправить файл в сообщество; его идентификатор включает сообщество, тип и данные. Клиент не пробует читать чужие старые каталоги.

Пользовательские эмодзи находятся в `communities/{community}/emojis/{hash}` и доступны только участникам. Старые эмодзи в профиле читаются только автором; существующий локальный кэш сохраняется. В новом облачном сообщении `Emojis` содержит не более 32 фиксированных слотов `e00`–`e31` с `Token`/`AssetId`. Это позволяет ограничить число на сервере без неподдерживаемого `numChildren`; клиент продолжает читать старые карты токен → хеш.

По согласованному решению аватары доступны вошедшим пользователям: `profiles/{uid}/Images/avatar` хранит один текущий аватар до 4 МиБ. Кэш по ревизии SHA-256 не меняется. Старые записи с `Kind = avatar` остаются читаемыми вошедшим пользователям, но неизменяемыми. `Info` профиля ограничивает поля и описание до 2000 символов; локальные пути не сохраняются в облако. Корень чужого профиля больше не читается, чтобы через него нельзя было обойти запрет `Files`.

**Прежнее утверждение «правила profiles подходят» относилось к работоспособности и не обеспечивало приватность вложений. Ветка hardening заменяет эту политику.** Живой голос/экран по-прежнему не проходят через базу.

Cloud Storage не подключён. Медиа расходуют квоту Realtime Database: Spark предоставляет 1 ГБ хранения и 10 ГБ скачиваний в месяц; Base64 добавляет примерно треть к размеру. Удаление черновика отменяет отправку, но не удаляет локальную копию. Автоматической очистки опубликованных облачных вложений пока нет. Для активного обмена большими файлами бесплатной квоты может не хватить. По действующим условиям Storage требует Blaze.

Официальные условия: [Realtime Database](https://firebase.google.com/docs/database/usage/limits), [оплата базы](https://firebase.google.com/docs/database/usage/billing), [требования Storage](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024).

## Закрытие приложения

Крестик скрывает окно и демонстрации в трей; голосовая сессия и захват продолжаются. Двойной щелчок по значку открывает окно. Для завершения выберите «Закрыть Wisp» в меню трея. Перед заменой файлов сборки завершайте приложение этим пунктом.

Зависимость WebRTC: SIPSorcery 10.0.17. [Её лицензия](licenses/SIPSorcery.md) включает дополнительное ограничение использования; файл включён в переносимую сборку. FFmpeg не используется.

Все участники разговора должны обновиться до этой версии. Старые клиенты с Opus/JPEG через SCTP не поддерживают SRTP-дорожки и управляющие каналы v2. Для ветки hardening правила меняются: используйте порядок выпуска ниже.

## Порядок выпуска правил и клиента hardening

1. Подготовьте и раздайте проверенную новую сборку, но пока не запускайте её против старых правил. Завершите старые клиенты через меню трея. Сохраните резервную копию правил и экспорт базы средствами владельца.
2. Владелец публикует **весь** `firebase/database.rules.json` через Firebase Console либо Firebase CLI с конфигурацией `firebase/firebase.json`. Агент этого не делает. Не используйте `src/Wisp.Desktop/firebase.json` как конфигурацию CLI.
3. После публикации запускайте новые клиенты у всех участников. Старые версии больше не смогут отправлять файлы в профиль или новые карты эмодзи. Локальный кэш не удаляйте.
4. Проверьте вложение и эмодзи на двух учётных записях сообщества, затем отсутствие доступа у третьей учётной записи вне сообщества.

Правила ограничивают отдельные объекты, но не являются глобальным ограничителем расходов. Открытая регистрация и возможность создавать новые сообщества всё ещё позволяют суммарно расходовать квоту. Владелец должен включить защиту от перебора email в Firebase Authentication, ограничить публичный API key разрешёнными API в Google Cloud Console, решить политику открытой регистрации, оценить App Check и настроить наблюдение за расходом базы. Никаких административных ключей в клиент добавлять не нужно.

ID сообщества пока остаётся постоянным приглашением: утёкшая ссылка позволяет вступить, а отзыв приглашения и исключение участника не реализованы. Возможное отдельное изменение — приглашения-токены с владельцем, сроком действия и отзывом; без отдельного согласия оно не выполняется.

STUN-сервер видит публичный IP подключающегося участника; SDP в Firebase содержит адреса ICE-кандидатов (включая локальные). Уведомление Wisp о выбранной паре содержит только типы `host`/`srflx`/`prflx`, без самих адресов. Между произвольными сетями связность не гарантируется.

## Поток сигналинга и удаление служебных записей

На клиента внутри голосового канала открыт один SSE-поток `communities/{community}/rtcRooms/{channel}`. Он содержит s0..s4 и ограниченные `events/sN/sN` с SessionId/Attempt/версией/временем, без SDP и IP. Это укладывается в лимит числа соединений Spark лучше, чем отдельный stream на каждую пару. При ошибке используется polling (не чаще 1 с в согласовании); auth_revoked обновляет токен.

SDP находится в `rtcSignals/{community}/{channel}/{from}/{to}`, trickle-кандидаты — в `rtcCandidates/{community}/{channel}/{from}/{to}`: Meta и c00..c63. Правила ограничивают размер, поля, совпадение попытки и свежих слотов обеих сторон. Записи старше 10 минут перестают читаться. Клиент чистит собственные старые префиксы при входе, текущие пары при штатном выходе и просроченные входящие записи своей пары при повторе; SessionId/ETag защищают новое окно от старой очистки. После аварии физические остатки могут лежать в базе: периодический trusted cleanup — отдельная опция (например Functions), не реализован и не развёрнут. TTL чтения не равен автоматическому удалению данных.

Время аренды/присутствия берётся из HTTP Date Firebase с последующим монотонным отсчётом, поэтому неточные часы ПК не должны блокировать вход. Если серверное время не получено, место не занимаетcя и показывается отдельная ошибка; запрет доступа больше не маскируется универсальным советом опубликовать правила.
