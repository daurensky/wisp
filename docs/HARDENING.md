# Wisp hardening: выполнение по фазам

Рабочая ветка: `codex/hardening`, база `codex/native-windows-p2p` на коммите `5f292cb`.
Изменения в исходную ветку и `main` не отправляются. Правила в рабочую Firebase-базу агент не публикует; производственные данные не изменяет и не удаляет.

## Согласованные решения

- Старые `profiles/*/Files` остаются в базе и читаются только автором. Новые вложения хранятся в сообществе; локальные копии старых файлов сохраняются.
- Аватары доступны авторизованным пользователям. Пользовательские эмодзи доступны только участникам соответствующего сообщества.
- По ответу владельца перед фазой 2 TURN не нужен. TURN-сервер, API временных учётных данных и relay-тест исключены из объёма работ. Настройка STUN и восстановление прямой связи остаются; ограничения NAT документируются.
- Приглашения-токены с отзывом не реализуются без отдельного согласования.

## Фаза 0: базовая линия

- `dotnet restore Wisp.sln`: успешно, Linux.
- `dotnet test tests/Wisp.Core.Tests -c Release --no-restore`: 30/30, Linux.
- `dotnet build Wisp.sln -c Release --no-restore`: успешно, 0 предупреждений / 0 ошибок, Linux (cross-build Windows-проектов).
- Подготовлен изолированный Realtime Database Emulator для проекта `demo-wisp-hardening`. Он не подключается к производственной базе.
- 4/4 базовых теста правил прошли в локальном эмуляторе. Тест P0-1 подтвердил, что посторонний вошедший пользователь читает голосовое вложение; после фазы 1 ожидание заменяется на запрет. Проверены также анонимное чтение, права SDP и пять фиксированных мест.
- Для локального запуска исправлено соблюдение существующего `NO_PROXY` только для loopback в установленных (не коммитящихся) копиях Firebase CLI/SDK: их версии принудительно использовали внешний прокси даже для `127.0.0.1`. Для остальных адресов унаследованный прокси сохранён. На CI без прокси используются неизменённые npm-пакеты.
- Исходники SIPSorcery читаются с коммита NuGet-пакета `08c2ed0ad72c423ca06950dee2e842488a219884`, а не из `main`.

WPF, Media Foundation, WASAPI и Windows.Graphics.Capture в Linux не выполнялись. Новые изменения этой ветки пока **не проверены на Windows**. Прежняя CI исходной ветки не считается проверкой новых изменений.

## Остальные фазы

1. Правила, новые пути файлов/эмодзи, порядок выпуска и тесты эмулятора.
2. Провайдер и настройка STUN без TURN по явному решению владельца. Секреты и сервер ретрансляции не добавляются.
3. Серверное время, попытки/восстановление, смена сети, сигналинг, очистка и тесты логики.
4. Запрос IDR, rate control, Windows.Graphics.Capture с GDI-резервом, пауза при сворачивании, минимальная адаптация сети; аппаратные MFT — только при подтверждённой поддержке.
5. FEC/PLC, адаптивный буфер, выбор и смена аудиоустройств, оценка системной обработки Communications.
6. CI правил, итоговые проверки и документация фактического поведения. Relay-тест не выполняется: TURN исключён владельцем.

Результаты каждой фазы, непроверенные сценарии и причины отложенных работ добавляются по мере выполнения.

## Фаза 1: приватность файлов и ограничение структуры

Новые вложения/голосовые переведены в узлы сообщества, старые оригиналы закрыты для всех, кроме автора. Новые эмодзи доступны участникам сообщества. Аватары используют один текущий слот, доступны вошедшим пользователям; старые публичные эмодзи закрыты. Правила ограничивают размер частей, число частей (32), полноту и неизменяемость файла, поля и типы профилей/сообщений/SDP. Метаданные файла содержат ровно четыре поля.

Максимум 32 разных эмодзи в новом сообщении проверяется фиксированными серверными слотами; прежняя карта токенов сохраняется только для чтения старой истории. Базовая тестовая утечка теперь проверяется как отказ. В эмуляторе прошли 13/13 тестов, включая реальный REST conditional PUT/412, запрет чтения через родителя, превышение размеров и лишние поля.

Порядок выпуска: сначала подготовить/раздать новый клиент и завершить старые процессы, затем владелец публикует строгие правила, затем запускаются новые клиенты. Автоматической миграции, удаления производственных данных и публикации правил нет. Детали — FIREBASE.md. Объектные ограничения не заменяют глобальный контроль квоты или защиту открытой регистрации.

После фазы 1: `dotnet build Wisp.sln -c Release --no-restore` — успешно, 0 предупреждений / 0 ошибок; `dotnet test tests/Wisp.Core.Tests -c Release --no-restore` — 31/31. 13-й тест эмулятора подтверждает, что обновление профиля не удаляет старые файлы и скалярные поля. Новые изменения пока **не проверены на Windows**.

## Фаза 2: настройка ICE без TURN

По явному решению владельца добавлены только провайдер STUN, проверяемый файл настроек и диалог «Сеть · STUN». Одна запись `RTCIceServer.urls` содержит одну строку URL; тесты пиров получают пустой список. Уведомления показывают тип номинированной пары без адресов. API сверены с SIPSorcery 10.0.17 по коммиту пакета. Сборка: 0 предупреждений/ошибок; core: 39/39. Новый диалог **не проверен на Windows**.

TURN-учётные данные, coturn/API и проверка `relay` намеренно не реализованы и не разворачиваются. Ограничения прямой связности сохраняются.

## Фаза 3: восстановление и сигналинг

Добавлены серверное время из HTTP Date с монотонным отсчётом, типизированные ошибки Firebase и ETag-занятие/продление места. Только 412 повторяет гонку места. Независимый watchdog останавливает транспорт через 40 секунд без продления, даже если HTTP-запрос завис. Старое окно не удаляет место другой сессии; штатная очистка пары использует проверку SessionId и conditional PUT.

Каждая новая попытка получает GUID Attempt. Задержки повторов — 2/5/15/30 секунд, затем остановка пары. `disconnected` через 5 секунд запускает ICE restart; через следующие 5 секунд без связи — новую пару. Для SIPSorcery 10.0.17 после restart явно повторно задаются сохранённые remote credentials и кандидаты, поскольку исходный метод очищает checklist. Смена адресов сети обрабатывается с задержкой 1,5 секунды.

SDP отправляется сразу, кандидаты передаются отдельно (Meta + c00..c63), очередь до remote description ограничена. Один SSE-поток открыт только внутри голосового канала: комната содержит места и 25 ограниченных wake-маркеров без SDP/IP. Личные SDP/кандидаты читаются отдельными защищёнными запросами пары. Поддержаны put/patch/keep-alive/cancel/auth_revoked, обновление токена и временный опрос с интервалом не менее секунды. Новые правила требуют Attempt и CreatedAt; смешивать версии клиентов нельзя.

Свежесть записи ограничивает чтение SDP/кандидатов 10 минутами и совпадающими свежими сессиями. При новой попытке участник может удалить просроченные входящие записи своей пары; при входе очищаются собственные старые префиксы. После аварии физические записи для отсутствующих участников могут оставаться: полную периодическую очистку должен выполнять отдельный доверенный сервер/Functions, не клиент. Такой сервис в этой ветке не разворачивается.

Эмулятор: 16/16. Core: 46/46, включая часы клиента, 412/403, watchdog, потерю места/старое окно, новую попытку и SSE с обновлением токена. Смена реальной сети и нативный ICE restart **не проверены на Windows**.

## Фаза 4: демонстрация

Запрос `screen-keyframe` проходит по заранее созданному events-каналу обоих транспортов. Ограничение раз в секунду есть у зрителя и у показывающего; запрос проверяет адресата/сессию показа. Плановый GOP — 3 секунды. Software MFT получает явные CBR, GOP и буфер 0,5 с через ICodecAPI; неподдержанный параметр отражается в статусе, HRESULT больше не игнорируется. Добавлен Windows-тест измерения размера потока до/после смены среднего битрейта и немедленного IDR (результат Windows CI записывается отдельно после запуска).

Захват вынесен в IScreenCapture. Основной backend — Windows.Graphics.Capture (окно/монитор, interop, курсор включён, рамка Windows сохранена, пересоздание пула при resize); GDI остаётся для всего рабочего стола и отказа WGC. В GDI добавлен курсор с hotspot. Свёрнутое окно повторяет последний кадр раз в секунду и сообщает зрителю о паузе; разворачивание продолжает поток. Закрытие источника завершает показ. Целевая платформа Desktop/его тестов — Windows 10 build 19041.

Из реальных RTCP RR/SR читаются потери, jitter и RTT для локального видео-SSRC. После трёх плохих отчётов поток снижается на 20% (не чаще раза в 5 с), затем снижается FPS. Если MFT отвергает live bitrate, частота снижается до 15 FPS с явным сообщением. Поток общий, UI объясняет умножение трафика на число зрителей. TWCCBitrateController в 10.0.17 найден, но без согласованного TWCC в эту минимальную RR-адаптацию не включён. RTP получает монотонные метки реального времени через публичный SendRtpRaw; для H.264 используется RFC 6184 FU-A, поскольку штатный SendVideo меняет только внутренний timestamp фиксированным шагом.

Аппаратные/asynchronous MFT отложены: измерить выигрыш CPU 1080p30/60 на GPU пользователя здесь нельзя. Программный кодировщик остаётся резервом; аппаратное ускорение не заявляется. WGC, сворачивание, DPI и фактическая нагрузка **не проверены на Windows**. Linux cross-build: 0 предупреждений/ошибок; core: 49/49 (включая реальную прямую пару с видео/аудио/файлом, RTP-часы и ограничение адаптации/IDR).

## Фаза 5: голос

RtcPeer передаёт ограниченное число пропусков RTP (0..3) как внутренние, не сериализуемые метаданные. Декодер пытается восстановить один пропуск через in-band FEC следующего пакета (Opus сам использует PLC, если LBRR отсутствует), несколько — через PLC. После этого декодируется текущий пакет. Тест на 300 кадров расширен восстановлением одиночных/серийных потерь для mono/stereo; проверяются счётчики попыток, rollover и отбрасывание дублей.

В голосовом микшере вместо полного сброса буфера используется ограниченное PCM-кольцо с priming 40–80 мс, оценкой джиттера и коротким cross-fade при удалении избыточного старого звука. Это не гарантирует фиксированную полную задержку: к ней добавляется задержка аудиоустройства.

Микрофон переведён на event-driven shared WASAPI, 48 кГц/16 бит/mono с системным преобразованием. Категория Communications задаётся через IAudioClient2.SetClientProperties до Initialize. Прямой IMMDevice.Activate используется для endpoint ID (ActivateAudioInterfaceAsync ожидает другой вид ID). При отказе категории есть явное предупреждение; наличие AEC/NS/AGC не обещается — обработка зависит от драйвера и Windows. Внешний WebRTC Audio Processing не добавлялся: лицензия/нативная сборка и измерение эха потребуют отдельного согласования.

В модальном диалоге «Звук · устройства» можно выбрать микрофон и выход голоса; настройки локальные audio.json. MMNotificationClient с debounce переключает отключённую гарнитуру на устройство связи по умолчанию и возвращает выбранное после подключения. Меняются только устройства, места и WebRTC-пары остаются; микшер/декодеры сохраняются. Выход мультимедиа чата/демонстрации пока следует системному выходу, это указано в диалоге. Индикатор speaking не добавлялся (необязателен).

Linux cross-build: 0 предупреждений/ошибок. Core: 53/53. Захват, системные эффекты, сравнение эха на колонках и hotplug **не проверены на Windows**; сценарии будут в TESTING.md. Windows CI фазы 4 `40326858481` прошла полностью: core 49, Desktop 4, publish ZIP. Она проверяет native H.264 (live bitrate/IDR) и темы, но не физический захват экрана/аудиоустройства.

## Фаза 6: CI и итоговая проверка

Добавлен отдельный Linux workflow `Firebase rules` (Node 24 / Java 21, demo-эмулятор без production credentials). Relay/coturn job исключён по решению владельца. Fake HTTP-тесты дополнены полным исчерпанием четырёх повторов; внутренние audio-gap метаданные проверены на отсутствие в JSON. Fallback polling дополнительно ограничен монотонным интервалом 1 с независимо от событий пробуждения. Linux core: 56/56; эмулятор: 16/16. Cross-build: 0 предупреждений/ошибок. Финальная CI подтверждается ниже после выполнения.

Дополнительный реальный тест обнаружил ограничение 10.0.17: restartIce очищает checklist, но оставляет завершённое состояние и NominatedEntry. Одного повторного SetRemoteCredentials недостаточно для новой nomination. После вызова restart wrapper сообщает restart-required для ранее номинированной пары, и mesh создаёт новые native peers/Attempt через ограниченный backoff. Приватные поля библиотеки не меняются, версия не заменяется. Новый тест проверяет очередь trickle до SDP, этот fallback и передачу голоса/команд после новой пары; это всё ещё не тест реальной смены Wi-Fi.

Windows CI фазы 5 [40328077856](https://github.com/daurensky/wisp/actions/runs/40328077856) прошла: core 53/53 (в том числе native Opus FEC/PLC), Desktop 4/4, build/publish ZIP. Реальные устройства и захват не тестировались. Из TRX фазы 4: CBR/буфер 0,5 с приняты; synthetic 320×192/30, окна по 3 с, после запроса 4→1 Мбит/с размер 1 607 899→695 780 байт (0,433). Это измерение реакции software MFT, не замер CPU или гарантия точного битрейта/1080p60.

Не сделано: TURN/coturn/API/relay по прямому указанию владельца; аппаратные async MFT из-за отсутствия подтверждённых CPU/GPU-замеров; внешний WebRTC DSP до согласования лицензии/сборки и измерения эха; speaking-индикатор необязателен. Периодическое trusted удаление аварийных SDP/candidates и отзывные приглашения только предложены, не развёрнуты. Политика TTL ограничивает чтение, а не физическое хранение. Владелец публикует правила только после раздачи клиента и завершения старых процессов, до запуска новых. Подробная таблица ручных сценариев/допущений — TESTING.md; требования к Auth/API key/App Check и постоянным приглашениям — FIREBASE.md.
