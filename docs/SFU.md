# Голос и демонстрация через свой VPS

Экспериментальный режим `codex/sfu-server`: Windows-клиент остаётся нативным WPF, а Linux-служба на Go/Pion пересылает уже сжатые RTP-пакеты. Firebase остаётся для входа, чата, профилей и присутствия. Сервер не микширует голос, не перекодирует видео и не записывает разговоры. TURN не устанавливается.

Для первого испытания: Ubuntu 26.04 amd64, VPS в Астане `89.126.195.20`, 1 vCPU / 2 GB / 25 GB, пять пользователей. Это целевая конфигурация, а не результат измерения производительности на этом VPS. Локальная проверка пяти реальных экземпляров транспорта SIPSorcery не проверяет качество микрофонов, Windows-захват, маршруты Казахстан—Корея и поведение под ограничением одного ядра.

## Установка на VPS

Команды выполняет владелец в уже открытом SSH-сеансе root. Пароли, SSH-ключи и Firebase service-account JSON не нужны в переписке.

```bash
apt-get update
apt-get install -y --no-install-recommends git
# Отдельный каталог: не заменять существующий checkout или чужие файлы.
git clone --branch codex/sfu-server --single-branch https://github.com/daurensky/wisp.git /opt/wisp-sfu-src
cd /opt/wisp-sfu-src
bash server/wisp-sfu/deploy/install.sh 89.126.195.20
```

Перед запуском установщик можно прочитать: `less server/wisp-sfu/deploy/install.sh`. Он скачивает SDK Go 1.27.3 с проверкой закреплённого SHA-256, собирает модуль с закреплёнными зависимостями (`go.mod`/`go.sum`), устанавливает `/usr/local/bin/wisp-sfu`, пользователя `wisp-sfu`, конфигурацию и TLS-сертификат в `/etc/wisp-sfu`, службу systemd. Сборка ограничена одним логическим процессором и целью Go heap 512 MiB. Для службы: GOMAXPROCS=1, GOMEMLIMIT=384 MiB, MemoryHigh=512M, MemoryMax=768M; это ограничения, а не замер потребления.

Скрипт не меняет SSH, firewall, swap и конфигурацию Firebase. При повторном запуске сохраняет существующие сертификат и настройки. После старта проверяет HTTPS с доверенным локальным сертификатом и печатает:

```text
URL: wss://89.126.195.20:8443/rtc
SHA-256: <64 шестнадцатеричных символа>
```

Отпечаток публичный, его можно передать всем пяти участникам. `server.key` остаётся только на VPS. Самоподписанный сертификат действует 365 дней; после его замены участникам нужен новый отпечаток. Домена для этого варианта не требуется.

Разрешить на **VPS**, включая firewall в панели провайдера:

| Назначение | Порт |
|---|---|
| Защищённый сигналинг и `/healthz` | 8443/TCP |
| DTLS/SRTP/SCTP через один ICE UDP mux | 50000/UDP |

Если UFW уже активен:

```bash
ufw status verbose
ufw allow 8443/tcp
ufw allow 50000/udp
```

Не включать UFW вслепую, не проверив правило своего SSH-порта. Для участников проброс портов домашнего роутера обычно не требуется: они открывают исходящее UDP-соединение к публичному VPS. Если сеть блокирует UDP, этот режим без TURN/TCP-relay не гарантирует подключение.

## Настройка всех Windows-клиентов

Нужна сборка **из `codex/sfu-server`**, а не предыдущий portable. В «Профиль и настройки → Сервер голоса»:

1. Включить «Передавать голос и демонстрацию через сервер».
2. Вставить URL из установщика.
3. Вставить SHA-256 сертификата из доверенного SSH-сеанса владельца.
4. Сохранить и заново войти в канал.

Все участники используют одинаковый адрес, отпечаток и режим SFU. Несовпадение сертификата закрывает соединение, автоматического перехода к P2P нет. Режим по умолчанию остаётся P2P, пока владелец не настроит сервер. Переключение действует со следующего входа в канал. Профиль, GIF, настройки микрофона и наличие пользователя в канале сохраняются.

Локальный файл `%LOCALAPPDATA%/Wisp/voice-server.json` имеет вид:

```json
{
  "Enabled": true,
  "Url": "wss://89.126.195.20:8443/rtc",
  "CertificateSha256": "<публичный отпечаток из установщика>"
}
```

Новые Firebase Rules не нужны: используется существующая аренда `communities/{community}/rtcRooms/{channel}/s0…s4`. Не запускать старые P2P-клиенты в одном канале с SFU-клиентами: они не обмениваются медиа друг с другом.

## Проверка после установки

```bash
systemctl --no-pager --full status wisp-sfu
journalctl -u wisp-sfu -n 50 --no-pager
ss -lntup | grep -E ':8443|:50000'
free -h
```

Открыть один канал на двух ПК, затем на пяти. Проверить одновременную речь, демонстрацию 1080p/60, отдельный звук демонстрации, mute/deafen, выход/повторный вход и разговор из трея. Один пользователь передаёт каждую дорожку на VPS один раз; сервер отправляет её до четырёх получателям. Шестой вход отклоняется и арендой, и сервером.

Если один видеопоток имеет 8 Мбит/с и четыре зрителя, только исходящий видеотрафик VPS составляет примерно 32 Мбит/с, или 14,4 GB за час (без накладных расходов). Несколько одновременных демонстраций умножают расход. При тарифе с 1 TB трафика это существеннее размера диска; уточнить у провайдера, какие направления учитываются и где смотреть расход. FPS/разрешение и битрейт задаёт клиент, SFU их не повышает.

На стороне VPS понадобится доступ HTTPS к Google Identity Toolkit и к используемой Realtime Database. Клиент отправляет короткоживущий Firebase ID token **только по WSS с проверенным pin**, сервер проверяет его у Google и читает членство, тип канала и свежую аренду от имени пользователя. Секретных административных ключей нет. Проверка доступа повторяется каждые 20 секунд; ID token обновляется клиентом каждые пять минут. Токены, SDP и IP участников не записываются приложением в журнал. Health endpoint не раскрывает пользователей/комнаты.

Медиа защищены DTLS/SRTP на каждом участке клиент—SFU. VPS имеет доступ к сжатым пакетам в оперативной памяти; это не сквозное шифрование между участниками.

## Устройство и ограничения

- Один publishing peer на пользователя: Opus mic, Opus share audio, H.264. До четырёх subscribing peers, каждый привязан к одному удалённому пользователю. Отдельные PCs сохраняют нынешний порядок дорожек нативного клиента и не требуют декодирования/микширования на сервере.
- Два существующих datachannel для команд и фрагментов файлов. Сервер пересылает данные только подписчикам источника, принимающий клиент назначает SenderId из согласованного источника, а не доверяет полю сообщения.
- RTCP/NACK обслуживаются Pion; PLI передаются источнику, отчёты потерь зрителей возвращаются кодировщику для снижения битрейта. Плановые IDR и существующие команды восстановления сохраняются.
- При пропаже аренды/сигналинга соединения закрываются. Автовосстановление SFU после смены сети пока не реализовано: повторно войти в канал. Звук ошибок ограничен существующей системой уведомлений.
- По умолчанию максимум пять сессий на весь VPS. `maxSessions` можно изменить до 20 для нескольких комнат, но ограничение пяти на комнату остаётся; ёмкость других конфигураций не проверена.
- Сервер ограничивает сообщения сигналинга, handshake, SCTP-буферы и трафик источников. Медленный клиент с переполнением исходящего SCTP-буфера отключается, файлы остаются доступны через Firebase. SRTP идёт отдельно.

## Проверки разработчика

```bash
dotnet build tools/Wisp.Sfu.Probe -c Release
cd server/wisp-sfu
WISP_SFU_PROBE="$(pwd)/../../tools/Wisp.Sfu.Probe/bin/Release/net8.0/Wisp.Sfu.Probe.dll" go test -race -count=1 -v -timeout 180s ./...
go vet ./...
```

Тестовый Firebase используется только внутри probe и Go test. В production-бинарнике нет тестового пароля или обхода авторизации. CI собирает Linux-бинарник и отдельно Windows portable. Автоматическая проверка включает пять клиентов, все 20 направлений подписки, доставку трёх типов RTP, двух SCTP-каналов, переписывание поддельного SenderId, файл 2 MB одновременно с видео и речью, mute/deafen, уход/повторный вход во время задержанного SDP-ответа, один общий UDP mux, отказ шестому/дублирующему пользователю и отказы доступа Firebase.

Для отката: отключить SFU во всех клиентах, заново войти в канал; `systemctl disable --now wisp-sfu` останавливает службу. Firebase и данные пользователей не удаляются.
